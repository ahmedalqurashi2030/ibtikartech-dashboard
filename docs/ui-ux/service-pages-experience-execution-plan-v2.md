# خطة تنفيذ V2 لتجربة صفحات الخدمات

## حالة الوثيقة

- الحالة: منفذة محليًا ومجتازة لبوابات QA بتاريخ 2026-09-02؛ لم تُرفع إلى GitHub.
- النطاق: فهرس الخدمات، فئات الحلول، وصفحات تفاصيل الخدمات في `public_preview`.
- الهدف: رفع وضوح القرار والثقة والتحويل، مع تقليل التكرار من دون إنشاء مكوّن
  شامل متشعب أو تغيير مصدر المحتوى قبل نضجه.
- هذه الوثيقة تستبدل التقرير الخارجي المبتور كخطة تنفيذ، ولا تستبدل عقود المشروع
  القائمة.

## الحالة التنفيذية النهائية

| المستوى | الصفحات | العقد المعتمد |
| --- | --- | --- |
| Level 1 — فهرس الخدمات | `services.html` | توجيه حسب الهدف، مقارنة العائلات، حلول مركبة، FAQ، CTA |
| Level 2 — عائلات الحلول | `ecommerce.html`، `websites.html`، `brand-content.html`، `growth.html`، `custom-systems.html` | ملاءمة ومسارات ونطاق وحدود وFAQ مشروط وخدمات مرتبطة |
| Level 3 — تفاصيل الخدمات | صفحات التفاصيل الست المسجلة في `SERVICE_PAGE_ROUTES` | نتيجة وملاءمة ونطاق ومخرجات ومتطلبات وFAQ وخدمات مرتبطة وCTA |

- بقي نموذج المجال `ServiceCategory -> Service` بلا طبقات تجارية جديدة.
- بقيت ثراء صفحة عرض Wagtail خارج تصنيف تفاصيل الخدمات.
- أصبحت الأنماط الثابتة فقط مشتركة عبر `service-primitives.css/js`، وبقي السرد
  والمحتوى المتخصص مملوكًا لكل صفحة.
- أزيل الاعتماد على السحب الأفقي في مسارات الجوال، وتوقفت التهيئة السينمائية
  على الشاشات الصغيرة وعند `prefers-reduced-motion`.
- أضيفت FAQ قرار حقيقية للعائلات الأربع التي كانت تفتقدها، وأضيفت الخدمات
  المرتبطة للتجارة الإلكترونية.
- اختبرت الصفحات الاثنتا عشرة في المتصفح عند 375×812 و768×1024 و1440×1000
  بلا overflow أو صور مكسورة أو IDs مكررة أو أخطاء console.

## مصادر الحقيقة الملزمة

تنفّذ هذه الخطة تحت العقود التالية، وعند التعارض تتقدم عليها:

1. `docs/ui-ux/current-design-contract.md` للهوية وطبقات CSS وملكية الواجهة.
2. `docs/ui-ux/content-ownership-contract.md` لملكية المحتوى وبوابات Wagtail.
3. `docs/ui-ux/comprehensive-qa-plan.md` لبوابات الاختبار والدمج والنشر.
4. `apps/public_preview/template_contract.py` لعائلات القوالب والـblocks القانونية.
5. `apps/public_preview/asset_contract.py` لملكية الأصول حسب المسار.
6. قرارات المجال في `AGENTS.md`، وخصوصًا بقاء الخدمات
   `ServiceCategory -> Service` وعدم إنشاء طبقات تجارية جديدة.

## قرار التنفيذ

لا يُنفّذ توحيد شامل للصفحات، ولا يُجمع CSS وJavaScript في ملفين ضخمين. التوحيد
المطلوب هو توحيد لغة القرار والمكوّنات التي ثبت تطابق وظيفتها، مع إبقاء السرد
والأدلة الخاصة بكل خدمة مملوكة لصفحتها.

لا يبدأ تحسين بصري جديد قبل إكمال QA للحالة الحالية؛ إذ تصف خارطة المشروع
الحالية المراحل البنيوية بأنها مكتملة وتحدد QA بوصفه البوابة التالية. أي اختلاف
بين الوثائق والكود يُعامل كعيب حالة أو تغيير غير معتمد، لا كإذن لتوسيع النطاق.

## حقائق الحالة الحالية

- فهرس الخدمات: `services.html`.
- عائلة فئات الحلول: `service_category_base.html`، وتستهلكها خمس صفحات:
  `ecommerce.html` و`websites.html` و`brand-content.html` و`growth.html` و
  `custom-systems.html`.
- عائلة تفاصيل الخدمات: `service_detail_base.html`، وتستهلكها ست صفحات:
  `store-launch.html` و`storefront-customization.html` و`store-redesign.html` و
  `product-page-optimization.html` و`ecommerce-growth.html` و
  `ecommerce-support.html`.
- يوجد تنفيذ محلي لـ`service-primitives.css` و`service-primitives.js`، لذا لا
  يُنشأ بديل جديد قبل تدقيقهما.
- مجلد العمل الحالي Git worktree مرتبط بالمستودع الرسمي على الفرع المحلي
  `service-pages-v2`. التغييرات الحالية محلية ومقصودة، ولم تنفذ عملية commit
  أو push.

## رحلة القرار المستهدفة

| المستوى | سؤال المستخدم | المهمة الأساسية للصفحة | الإجراء الأساسي |
| --- | --- | --- | --- |
| فهرس الخدمات | ما المجال المناسب لمشكلتي؟ | توجيه المستخدم إلى فئة صحيحة بسرعة | استكشاف الفئة |
| فئة الحلول | أي خدمة تناسب وضعي ومرحلتي؟ | المقارنة والتأهيل الذاتي وفهم الفرق | فتح تفاصيل الخدمة |
| تفاصيل الخدمة | هل أثق بهذه الخدمة وهل تناسبني الآن؟ | إزالة المخاطر وشرح النطاق والنتيجة | بدء استفسار مؤهل |

الاتساق يعني بقاء هذا التسلسل مفهومًا عبر الصفحات، وليس نسخ مخزون الأقسام نفسه
في كل صفحة.

## سياسة المحتوى والأقسام

### عناصر مطلوبة لكل صفحة تفاصيل

- عنوان نتيجة واضح، لا اسم خدمة مجرد.
- وصف مختصر يحدد العميل المناسب والمشكلة التي تُحل.
- إجراء أساسي واحد ظاهر، وإجراء ثانوي أقل بروزًا عند الحاجة.
- نطاق واضح: ما يدخل، ما لا يدخل، والمخرجات.
- مسار تنفيذ أو توقع زمني صادق.
- متطلبات بدء العمل من العميل.
- أسئلة واعتراضات حقيقية مرتبطة بالخدمة.
- خدمات مرتبطة بسبب مفهوم، لا بطاقات عامة فقط.

### عناصر مشروطة بالدليل والحاجة

- FAQ عندما توجد اعتراضات متكررة فعلًا.
- Anatomy أو Gallery عندما يكون الشرح البصري ضروريًا لفهم المخرج.
- Timeline عندما تختلف المراحل أو التبعيات ويحتاج العميل لتوقعها.
- Pricing guidance عندما يمكن عرضه من دون تضليل أو وعود غير منضبطة.
- Case study أو testimonial عندما توجد موافقة ومصدر يمكن التحقق منهما.

### عناصر ممنوعة

- شهادات أو أرقام أو شعارات عملاء غير موثقة.
- صور عامة لا تمثل الخدمة أو النتيجة.
- نص placeholder في أصول إنتاجية.
- مؤثرات 3D أو حركة زخرفية بلا فائدة قرار واضحة.
- فرض قسم فارغ لمجرد المحافظة على تطابق الصفحات.

## نموذج ملكية الواجهة

| الطبقة | ما تملكه | ما لا تملكه |
| --- | --- | --- |
| Global | tokens وbase وshell والطباعة | سلوك صفحة خدمة |
| Service primitive | عناصر مستقرة بلا منطق صفحة، مثل heading وbreadcrumb | Gallery أو tabs أو محتوى تجاري |
| Service pattern | نمط متكرر بعقد كامل، مثل decision tabs أو CTA card | شروط حسب اسم الصفحة |
| Page family | الهيكل والأصول المشتركة داخل المستوى نفسه | سرد جميع الصفحات |
| Page-owned | الأدلة والمحتوى والتجارب الفريدة | إعادة تعريف shell أو tokens |

لا يُستخرج مكوّن إلا بعد ظهوره بالوظيفة والبنية والسلوك نفسيهما في ثلاث صفحات
على الأقل، أو عندما يكون جزءًا ثابتًا مثبتًا من عقد العائلة.

## خطة التنفيذ المرحلية

### المرحلة 0 — استعادة خط أساس قابل للتدقيق

#### العمل

1. تنفيذ العمل داخل clone فعلي للمستودع الرسمي وعلى branch مخصص.
2. تسجيل SHA وbranch و`git status` قبل أي تعديل.
3. مقارنة الملفات المحلية غير المتعقبة أو المعدلة بالمستودع، خصوصًا
   `service-primitives.css/js` و`store-launch.html`.
4. عدم نسخ أي تغيير محلي إلى الفرع قبل فهم مصدره ومراجعته.

#### بوابة الخروج

- Git worktree صالح ونظيف أو قائمة تغييرات محلية موثقة ومقصودة.
- SHA أساس معروف.
- لا أسرار أو ملفات بيئة ضمن الفرق.

### المرحلة 1 — QA للحالة الحالية وخريطة الأصول الفعالة

#### العمل

1. تشغيل اختبارات Django والعقود المذكورة في خطة QA الشاملة.
2. استخراج CSS وJS الفعليين لكل route بعد تطبيق وراثة Django blocks، لا بمجرد
   عدّ وسوم القوالب المصدرية.
3. تسجيل المالك والمستهلك والحجم وسبب التحميل لكل أصل.
4. التقاط baseline عند 375×812 و768×1024 و1024×900 و1440×1000 للصفحات
   الممثلة لكل عائلة.
5. فحص keyboard وfocus وRTL و200% zoom وreduced motion وعدم وجود overflow.

#### بوابة الخروج

- تقرير عيوب مصنف P0/P1/P2 مع دليل قابل لإعادة الإنتاج.
- لا Critical أو Serious غير موثق في فحص الوصول.
- خريطة تحميل فعالة تكشف التكرار الحقيقي لكل route.
- صور مرجعية ونتائج أداء محفوظة مع SHA.

### المرحلة 2 — إصلاحات P0 في التنفيذ المشترك

#### نطاق البداية المثبت

- إكمال عقد ARIA لتبويبات القرار: `tablist` وIDs و`aria-controls` و
  `aria-labelledby` و`aria-selected`.
- roving `tabindex` ودعم ArrowLeft/ArrowRight وHome/End بما يلائم RTL.
- `focus-visible` واضح لكل عنصر تفاعلي.
- احترام `prefers-reduced-motion` في CSS وJavaScript والتمرير البرمجي.
- الحفاظ على deep links وعدم تعطيل سلوك الرابط أو history بلا بديل كامل.
- رفع مساحات اللمس المستهدفة إلى 44×44px حيث يمكن، مع عدم النزول عن WCAG.
- منع Header وnavigation وsticky CTA من حجب التركيز أو آخر محتوى الصفحة.
- إزالة placeholder assets والنصوص المؤقتة.
- جعل التهيئة idempotent، وعدم إضافة listener مرتين عند التحديث الجزئي.

#### قاعدة التغيير

يُصلح كل سلوك في مالكه الحالي أولًا. لا يُقسّم الملف أو يُدمج إلا إذا أثبتت
خريطة الأصول أن النقل يقلل الازدواج بلا توسيع لنطاق التحميل.

#### بوابة الخروج

- اختبارات تفاعل للوحات القرار والتنقل وCTA وFAQ وHotspots.
- اجتياز keyboard وRTL وreduced motion عند المقاسات الأساسية.
- لا تغيير بصري غير مقصود مقارنة بالـbaseline.

### المرحلة 3 — Pilot تجربة خدمة واحدة

تستخدم `store-launch.html` بوصفها Pilot لأنها تحتوي معظم الأنماط المطلوبة، لكن
لا تصبح مرجعًا لبقية الصفحات تلقائيًا.

#### العمل

1. تحديد فرضية الصفحة والجمهور والاعتراضات قبل تعديل الأقسام.
2. اعتماد ترتيب المحتوى: نتيجة الخدمة، الملاءمة، النطاق، الدليل، العملية، CTA.
3. استبدال أي placeholder بأصل حقيقي مناسب أو إزالة القسم حتى يتوفر الأصل.
4. مقارنة الرحلة مع `product-page-optimization.html` لاختيار المكوّن الأفضل
   وظيفيًا، لا الأغنى بصريًا.
5. ربط CTA وanalytics بعقد التحويل الحالي دون إنشاء Lead عند نقرة WhatsApp.

#### بوابة الخروج

- اختبار مهمة: يستطيع مستخدم جديد تحديد الملاءمة والنطاق والخطوة التالية.
- موافقة بصرية على الجوال والكمبيوتر والـRTL.
- لا regression في SEO أو analytics أو الروابط المسماة.
- قرار موثق لكل pattern: تعميم، إبقاء page-owned، أو حذف.

### المرحلة 4 — استراتيجية الأدلة والتحويل

#### العمل

1. جرد الأدلة المتاحة: حالات، نتائج، شهادات، عمليات، ضمانات وحدود.
2. منع نشر أي دليل بلا مصدر وموافقة.
3. تحديد CTA أساسي واحد لكل مستوى من رحلة الخدمات.
4. قياس funnel من مشاهدة الفئة إلى فتح التفاصيل ثم بدء وإكمال الاستفسار.
5. إضافة أحداث ذات أسماء وpayloads متوافقة مع عقد analytics الحالي فقط.

#### بوابة الخروج

- مصفوفة محتوى لكل صفحة تبيّن المطلوب والمتاح والناقص والمالك.
- تعريف صريح لمؤشرات النجاح وخط أساس سابق للتغيير.
- لا conversion event قبل نجاح الخادم، و`whatsapp_click` يبقى تحليليًا فقط.

### المرحلة 5 — الترحيل بحسب العائلة

#### الترتيب

1. بقية صفحات تفاصيل الخدمات، صفحة واحدة في كل مرة.
2. فئات الحلول الخمس، مع الحفاظ على اختلاف رحلة كل فئة.
3. فهرس الخدمات بعد استقرار الوجهات التابعة له.

#### قواعد الترحيل

- لا يُجمع تغيير المحتوى مع نقل ملكية الأصول في PR واحد.
- لا تُضاف variants لمجرد معالجة صفحة واحدة.
- لا يُحذف أصل قديم حتى يثبت البحث والـrendered HTML عدم وجود مستهلك.
- كل صفحة تمر بالاختبارات والصور المرجعية قبل الانتقال إلى التالية.

#### بوابة الخروج

- مالك واحد لكل سلوك JavaScript.
- لا CSS/JS route-scoped خارج المستهلكين المسجلين.
- اختلافات الصفحات موثقة ولا تعتمد على شروط اسم الصفحة داخل المكوّن.

### المرحلة 6 — التنظيف والأداء

#### العمل

1. إزالة الأصول والselectors المتقادمة المثبت عدم استخدامها.
2. تقليل القواعد المتطابقة بناءً على AST أو مقارنة دقيقة، لا تشابه الأسماء.
3. تحسين الصور إلى WebP/AVIF مع أبعاد و`srcset/sizes` حيث يلزم.
4. تأجيل الصور أسفل الطية وحجز مساحاتها لمنع CLS.
5. فحص listeners والـIntersectionObservers وعمليات القراءة/الكتابة أثناء scroll.

#### بوابة الخروج

- اجتياز أهداف Lighthouse والأداء في `comprehensive-qa-plan.md`.
- لا duplicate assets في HTML الفعلي.
- كل حذف مدعوم باختبار عقد أو قائمة مراجع صفرية.

### المرحلة 7 — QA النهائي والإطلاق

تنفذ خطة `comprehensive-qa-plan.md` كاملة على SHA النهائي. لا دمج ولا نشر عند
فشل أي بوابة. النشر والـrollback عمليتان مستقلتان وتتطلبان موافقة صريحة.

## مصفوفة التحقق الأدنى لكل صفحة

### Rendering والعقود

- استجابة GET تساوي 200.
- `main-content` وIDs فريدة.
- title وdescription وcanonical وOpen Graph وJSON-LD صحيحة.
- الروابط الداخلية Django named URLs.
- لا تكرار للأصول في HTML الناتج.

### الوصول

- ترتيب headings منطقي.
- كل صورة لها alt مناسب أو alt فارغ إذا كانت زخرفية.
- الأيقونات الزخرفية مخفية عن accessibility tree.
- جميع الإجراءات قابلة بلوحة المفاتيح مع focus ظاهر وغير محجوب.
- التبويبات وFAQ وHotspots تعلن الاسم والحالة والعلاقة الصحيحة.
- التباين 4.5:1 للنص العادي و3:1 لعناصر الواجهة ذات المعنى.
- الصفحة صالحة عند 200% zoom ومع reduced motion.

### الجوال وRTL

- لا overflow أفقي غير مقصود عند 320 و375px.
- أهداف اللمس مريحة ومتباعدة.
- Sticky UI يحجز مساحة للمحتوى وsafe-area.
- اتجاه الأسهم وترتيب التبويبات والمحتوى صحيح في RTL.
- لا يعتمد إجراء أساسي على hover أو swipe فقط.

### التحويل والثقة

- CTA أساسي واحد واضح.
- النطاق والاستثناءات والتوقعات غير مضللة.
- كل شهادة أو رقم أو شعار موثق.
- analytics لا يكرر الأحداث ولا يحول النقرة إلى Lead.
- نجاح الاستفسار لا يسجل إلا بعد استجابة الخادم الناجحة.

## Definition of Done

لا تعد مبادرة صفحات الخدمات مكتملة إلا إذا تحقق الآتي:

1. رحلة القرار واضحة في المستويات الثلاثة، من دون فرض أقسام غير مفيدة.
2. لا عيوب وصول Critical أو Serious، مع تحقق يدوي للوحة المفاتيح وRTL.
3. لا أصل route-scoped مكرر أو محمل خارج مستهلكه.
4. لا placeholder أو دليل تجاري غير موثق.
5. الصور والأداء يحققان بوابات QA المعتمدة.
6. اختبارات Django والعقود والـvisual regression ناجحة على SHA موثق.
